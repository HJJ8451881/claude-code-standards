# claude-code-standards

我平常用 Claude Code 進行日常開發的實際配置。重點不是讓 AI 寫得快，而是讓 AI 寫出的東西符合工程標準——型別、例外處理、測試、文件慣例都要到位，不是「能跑就好」。這個 repo 展示我怎麼做到這件事，以及這個做法本身的取捨。

## 設計理念

**全域極簡，領域規則下放到 `skills/`。** `CLAUDE.md` 每次對話都會被載入，塞進去的東西越多，模型對真正相關的規則的注意力就被稀釋得越嚴重，也白白浪費 context。所以全域檔案只留下「不管做什麼專案都成立」的偏好（回覆風格、環境限制、工作記錄慣例），其餘按領域拆成 `skills/`，由 Claude Code 依任務內容自己判斷要不要載入。這代表 Python 專案不會因為我同時也做 Raspberry Pi 部署而被迫看到一堆不相關的規則。

**規則要可執行、可驗證，不能只是「請寫好一點」。** 「型別要寫完整」「外部呼叫要包 try/except 並 log」都是可以直接檢查有沒有做到的規則。模糊的指示（例如「程式碼品質要高」）在實務上幾乎不會改變輸出，因為模型沒有辦法拿它來自我檢查。這個原則貫穿這裡每一份 `skills/*.md`。

**AI 負責實作，人負責需求拆解、架構判斷與程式碼審查。** 這條界線要講清楚：我會讓 Claude Code 直接寫 CRUD、測試、重構這類有明確規格可循的工作；但「這個 schema 改動安不安全」「這個 migration 要不要人工看過」這種需要對系統整體風險負責的判斷，我不會交出去（見 `examples/project-CLAUDE.md` 的「Out of scope」一節）。工具負責產出，人負責決定產出對不對、該不該做。

## 配置說明

| 檔案 | 解決的問題 |
|---|---|
| `CLAUDE.md` | 全域偏好與環境限制——回覆風格、conda/pip 的坑、工作記錄慣例。刻意保持精簡，只做路由。 |
| `skills/python-standards.md` | 型別、logging、例外處理、測試、檔案拆分的具體門檻。每一條都是可檢查的規則，不是原則宣示。 |
| `skills/git-helper.md` | Commit 訊息與版本化設計文件的產生規則，把「先讓使用者確認再 commit」「不要自作主張 `git add`」寫成硬規則，因為這是最容易被抄捷徑的地方。 |
| `skills/session-handoff.md` | 跨 session 的交接慣例：新的一次對話該先讀什麼、記錄該用什麼骨架、未驗證的事要老實寫「未驗證」而不是含糊帶過。 |
| `skills/handover-docs.md` | 產出交接文件、操作手冊、SOP 的訪談問題集與章節骨架——這類文件的價值在於問出「只有當事人知道、機器看不出來」的資訊。 |
| `skills/to-spec.md` / `skills/grilling.md` / `skills/grill-me.md` | 一組配對：`grilling` 用design-tree方式把一個想法逼問到每個分支都有答案；`to-spec` 把已經談定的結論整理成規格文件，且明確規定「不重新訪談」。兩者刻意不能混用。 |
| `skills/ardupilot-params.md` | ArduPilot 參數與 MAVLink/DroneCAN 的具體眉角——版本間參數改名、RTCM 分片限制這類容易在文件裡查不到、但踩過一次就忘不了的細節。 |
| `skills/raspberry-pi-deploy.md` | Raspberry Pi 5 + Wayland 部署的常見坑：systemd 訊號處理、UART/GPS 搶埠、遠端桌面工具的相容性問題。 |
| `skills/zhtw-ui-translation.md` | 介面在地化的用詞表與掃描遺漏字串的方法，包含「語言選得到但完全沒作用」這類 i18n 框架特有的靜默失敗模式。 |

## 實際效果

有沒有載入 `python-standards.md`，對同一個任務的輸出差多少？見 [`examples/before-after.md`](examples/before-after.md)——同一個模型、同一句需求，每組跑三次的 A/B。

| 面向 | before | after |
|---|:---:|:---:|
| 型別註解 | 0 / 3 | 3 / 3 |
| `logging` | 0 / 3 | 3 / 3 |
| `print()` 輸出結果 | 3 / 3 | 0 / 3 |

原始 JSON 輸出（含 session ID、模型 ID、token 用量、成本）全部保留在 [`examples/raw/`](examples/raw/)，重現腳本是 [`examples/reproduce.sh`](examples/reproduce.sh)。

結論比想像的微妙：無規範那版並不差——有 docstring、有空值處理、會主動說明樣本與母體標準差的差別。它缺的是**你沒開口要就不會有的東西**。規範真正省下的不是「把爛程式碼變好」，而是省下每次都要記得去要。

文件裡也記了我在這個實驗中被自己的資料打臉兩次的經過，以及這批 raw 資料本身的一個實驗瑕疵——N=1 在兩個方向都騙過我。

`examples/project-CLAUDE.md` 則示範專案層級的 `CLAUDE.md` 該長什麼樣子：只放「這個專案特有」的東西，其餘都交給全域配置。

## 使用方式

1. 把 `CLAUDE.md` 複製到 `~/.claude/CLAUDE.md`（或合併進既有內容）。
2. 把 `skills/` 底下需要的檔案複製到 `~/.claude/skills/<name>/SKILL.md`（每個技能一個資料夾）。
3. 依自己的環境調整 `CLAUDE.md` 裡的偏好與限制——這些是我的個人習慣，不是必須照抄的規範。
4. 新專案如果有專屬慣例，照 `examples/project-CLAUDE.md` 的模式另開一份專案層級的 `CLAUDE.md`，不要把專案特例塞回全域檔案。

## 心得

- **規則寫太長，反而會被忽略。** 早期我把很多細節塞進全域 `CLAUDE.md`，後來發現模型對後段規則的遵從度明顯下降——這也是後來把大部分內容搬進 `skills/` 按需載入的直接原因。
- **規則要具體到可驗證，「請注意程式碼品質」這種指示基本沒有用。** 每次我發現某條規則沒被照做，幾乎都是因為那條規則本身寫得太抽象，模型無從判斷自己有沒有做到。
- **不是所有任務都適合交給 AI 自己判斷完就做。** 會影響資料完整性、或需要對系統整體風險負責的變更（schema migration、正式環境的操作），我會要求先講清楚再動手，而不是讓工具自己拿主意——這類界線需要在配置裡明講，不然它不會自己浮現。
- **這套配置目前偏向我自己的工作型態**（嵌入式、UAV、SDR 領域），對 Web 開發或資料科學這類完全不同的領域，`skills/` 底下的具體規則不會直接適用，但「全域極簡＋領域規則分離＋規則要可驗證」這個方法論本身是可以搬過去的。
