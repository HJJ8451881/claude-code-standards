# 設計文件 v1.0：claude-code-standards

日期：2026-08-20

## 為什麼有這個 repo

大部分「我會用 AI 工具」指的是在對話框裡問問題。這個 repo 要展示的是另一件事：**如何讓 AI 產出符合工程標準的程式碼，而不是能跑就好。**

所以 repo 的主體是 README 的方法論論述加上實際在用的配置檔，不是程式碼量。判斷這個 repo 成不成立的標準是：陌生人讀完 README，能不能理解這套方法論並自己套用。

## 目錄結構

```
claude-code-standards/
├── README.md              ← 核心產出
├── CLAUDE.md              ← 全域配置（極簡，只做路由）
├── skills/                ← 領域規範，按需載入
├── examples/
│   ├── project-CLAUDE.md  ← 專案層級配置範本
│   └── before-after.md    ← 有無規範的產出對照
└── _doc/
    └── v1.0.md            ← 本文件
```

## 內容整理原則

**CLAUDE.md（全域）** 維持極簡設計——只做路由，把細節下放到 `skills/`。README 要說明這個設計的理由：全域檔案每次對話都會載入，塞太多會稀釋注意力也浪費 context；領域規範按需載入才有效。這個取捨本身就是論點，必須寫出來，而不是只把檔案放上去。

**skills/** 每份規範一個檔案，格式統一（YAML frontmatter + 條列規則）。規則要具體到可驗證——「型別要寫完整」可以檢查，「請寫好一點」不能。

**examples/before-after.md** 挑一個小任務（讀 CSV 並統計），並列兩份產出：無規範版本（能跑，但沒型別註解、用 `print`、沒有例外處理、沒測試）與有規範版本（完整型別、`logging`、try/except、附測試）。

這份對照是整個 repo 說服力最強的地方——它把抽象的「我會管控 AI 產出品質」變成看得見的差異。也要誠實標註這個範例的限制：規範真正的價值在大型跨檔案變更中更明顯，但那種案例沒辦法濃縮成一頁對照表。

## 敏感內容處理

原始配置直接來自個人的 `~/.claude/`，其中含有工作環境資訊。整理進 repo 時逐檔移除：

- 公司名稱、部門名稱、專案代號、客戶名稱
- 內部系統路徑、主機名稱、IP、埠號、憑證
- 含機構識別的報告格式範本（整份移除，或改寫成通用的技術報告結構）
- 任何內部文件內容或實際參數值

ArduPilot 參數、Raspberry Pi 部署這類屬於公開技術知識，可以保留——但要確認裡面沒有夾帶特定專案的設定值。

判準：這份檔案如果被現在的主管看到，會不會有問題？會的話就刪。

## 驗收標準

- 陌生人 clone 下來能直接用
- README 讀完能理解方法論，而不只是看到一堆設定檔
- 全 repo 沒有任何公司相關資訊
- 篇幅克制——這是配置 repo，不是長篇論文
